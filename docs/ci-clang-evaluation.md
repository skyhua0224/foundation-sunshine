# Windows 构建改用 Clang 的评估

2026-11-16。结论在最后一节「建议」:**有条件采用**。
本文有两部分数据:前面是固定主机上 GCC 与 Clang 交错重复的 A/B(本次);「附」是 2026-11-15 在托管 `windows-latest` 上的测量(当时的结论是端到端没有可靠收益)。
两者不矛盾:托管 runner 的 CPU 型号差异约 1.6 倍,盖过了编译器之间的差异,同一台机器上才看得清。

## 方法与环境

**固定主机。** 一台 24 线程主机(i7-13700KF,31 GB),全部构建在同一台机器上、同一时段交错进行(每轮顺序:冷 GCC、冷 Clang、热 GCC、热 Clang)。
主机同时跑着其他构建任务(每次构建开始时的 1 分钟平均负载 1–16,见逐次记录),所以墙钟含噪声;
同时报告构建进程树(含 Wine 子进程)的 CPU 时间,取自 cgroup 记账,它基本不受排队影响(冷 GCC 三次 6292、6294、5710 s)。

**工具链。** MSYS2 UCRT64 的软件包原样解包:GCC 16.2.0(Rev7)、Clang 与 LLD 23.1.5、CMake 4.5.0、Ninja 1.13.2、ccache 4.14.2、Boost 1.92.0(源码构建),
编译器是 Windows 版 `.exe`,在 Wine 11.14 下运行,不是交叉编译;与托管 runner 上的区别只在系统调用层(CPU 时间中系统态占 17%–26%)。
被测提交是 `22e2c4ea`(本分支的 Clang 改动),配置与 CI 的「Configure Windows」一致:`BUILD_TESTS=ON`、`BUILD_TRAY_TESTS=ON`、ccache 启动器、
`CCACHE_DEPEND=1`、`CCACHE_SLOPPINESS=pch_defines,time_macros`、`-j8`。与 CI 不同的只有:GUI 包用占位文件、`DRIVER_DEPS_REQUIRED=OFF`、
Boost 源码目录在各次构建间共享(避免每次下载 690 MB;目录名保留 `_deps`,项目的预编译头规则据此跳过 Boost)。

**四种配置。** `gcc`(当前默认,不用预编译头)、`clang`(拟采用:LLD + 预编译头)、`clang-nopch`、`gcc-pch`。后两种只用来把编译器和预编译头的效果拆开。
**冷**=构建目录和 ccache 都删除,**热**=只删构建目录、保留 ccache(命中 99.4%,未命中的 6 个单元每次相同)。
**编译累计**是 Ninja 日志里所有 `.obj` 的耗时之和(跨并行任务相加),**链接累计**是所有 `.exe`、`.dll`、`.a` 的耗时之和。

**顺序与舍弃的运行。** 前两种配置(`gcc`、`clang`)按上面的顺序交错 3 轮;后两种在主矩阵和测试之后各运行 2 次冷构建,不与前两种逐轮配对。
试跑中发现:共享的 Boost 源码目录如果名字里没有 `_deps`,项目的预编译头规则会把预编译头套到 Boost.Log 上,Clang 23 因目标特性不一致拒绝编译(`dump_ssse3.cpp`)。
这是测试装置的问题,CI 里 Boost 在 `build/_deps` 下不受影响;修正目录名后全部重跑,试跑的数字(GCC 冷构建 1146 s,当时没有 CPU 记账)没有计入。

**没有做的。** 没有在托管 runner 上重做;没有在原生 Windows 上跑完整套测试(这套测试会碰驱动、音频设备、注册表和 NVIDIA 配置,不在维护者的虚拟机上运行,见「正确性」)。

## 运行时微基准

三个程序用各自编译器、项目自己的优化选项(`-O3 -DNDEBUG`,C++ 为 `-std=gnu++23`)构建,同一颗 CPU 核固定,两个编译器交替运行 11 轮,取每轮内部最佳值的中位数:
- FEC:项目自带的 nanors Reed-Solomon,40 个数据分片加 8 个校验分片,每片 1408 字节,与实验分支 `ci/lab31-clang-1` 的 `fec_bench.c` 相同;解码时丢 4 片。目标文件取自上面各自的冷构建。
- 数据包拆分:`src/stream.cpp` 里 `stream::concat_and_insert` 的原文(未改动),一帧 200 KB、每片 1392 字节、每片插入 16 字节包头。
- 调度器:`src/streaming/video_pacing.h` 的 `video_packet_slot`(`video_pacing_unit_tests` 测的函数)。

| 指标 | GCC | Clang | Clang/GCC | 范围(GCC;Clang) |
|---|---|---|---|---|
| FEC 编码 MB/s | 5367 | 5341 | 0.995 | 5256–5522;5266–5535 |
| FEC 解码(丢 4 片)MB/s | 10869 | 10300 | **0.948** | 10429–11005;10213–10570 |
| 数据包拆分 MB/s | 5120 | 5076 | 0.991 | 4893–5342;5007–5277 |
| 调度器槽位计算 百万次/s | 178.0 | 159.5 | 0.896 | 176.0–186.2;157.3–160.1 |

这是在固定主机上用 Wine 运行 Windows 程序得到的数字;被测的是纯计算,没有系统调用,Wine 不参与。
**没有看到托管 runner 上那次「FEC 编码快 12%、解码快 14%」**:这里编码持平、解码反而慢 5%。托管 runner 的 CPU 型号不同,那次的差别可能来自 CPU 而不是编译器。
调度器函数一次约 6 ns,每个数据包只调用一次,差别可以忽略。

**Windows 虚拟机上的运行:未取得。** 脚本已就绪(只运行这三个小程序,固定一个核,运行完删除自己的目录),带在场保护:
维护者标记虚拟机忙、有游戏进程、虚拟机 CPU 高于 30% 时拒绝运行。写文档时(05:45)虚拟机上有游戏进程在运行(自 00:10 起有交互会话),保护脚本按设计拒绝运行;
脚本每 5 分钟重试,拿到结果后补进本节。
没有找到可用的「固定合成码流下的主机 CPU 占用」测量工具(仓库里没有),也没有独立的音频路径基准,所以这两项没有做。

## 正确性

**原生测试套件,各 10 次交错运行**(与 CI 的「Run native tests」步骤同样参数:`-j4 --no-tests=error --timeout 600`),共 86 个 ctest 条目。
这套测试会碰驱动安装、音频设备、注册表和 NVIDIA 配置,不在维护者的虚拟机上运行,而是在固定主机上用 Wine 运行(一次约 17 s)。
所以绝对通过数不是目标,目标是**两个编译器之间的差异**:

- 两个编译器每次都失败的条目相同:`nvprefs_unit_tests`、`hdr_encoding_unit_tests`、`pre_encode_filter_unit_tests`、`session_auth_routes_unit_tests`、
  `reverse_tunnel_probe_build`、`reverse_tunnel_transport_tests`、`test_sunshine`(1025 个用例 997 个通过,其余是跳过的用例和因没有 GPU 编码器而初始化失败的 `EncoderVariants/EncoderTest`),另有 `ds5_native_usbip_smoke` 被跳过。
  原因都是 Wine 里没有对应的 GPU、驱动或 NVAPI。
- **只在一个编译器下失败的条目:没有;只在一个编译器下失败的用例:没有**(各 10 次)。
- `http_safety_unit_tests`(此前的竞态修复)、`beast_http_unit_tests`、`poster_unit_tests`、`pairing_pending_unit_tests` 等在两边 10/10 通过。
  托管 runner 上 `Poster` 测试在 Clang 下 17 次里失败 2 次、GCC 8 次里 0 次(Windows 文件共享冲突,见附),Wine 里没有这个语义,所以这次不能复现也不能排除。

**警告:** 两个编译器的所有构建(`-Wall`)均为 0 条警告。两个编译器各自保留的 `-Wno-` 选项是原来就有的,没有新增笼统的屏蔽。

**新发现的运行库与链接差异(Clang 构建独有,均已验证可修):**

1. **多导入 `libiconv-2.dll`。** 在 PATH 里没有 MSYS2 的环境启动 Clang 版 `sunshine.exe`,加载器报 `0xc0000135`(DLL 找不到);GCC 版正常启动。
   原因:链接行里有一个显式的 `libiconv.dll.a` 导入库(紧跟在 Boost.Locale 之后,应来自它的 iconv 依赖),LLD 用它解析了 iconv 符号。
   最小例子里,导入库排在静态库前面时 LLD 和 GNU ld 都会产生这个导入;GCC 版 `sunshine.exe` 恰好没有(符号先被静态库解决,原因没有深查),不能依赖这个巧合。
   CI 里的测试程序在装了 MSYS2 的机器上运行,这个问题不会暴露;用户机器上会直接打不开。
   验证:从链接行去掉这个显式导入库,`-liconv` 在 `-static` 下取静态库,新的 `sunshine.exe` 85.1→86.2 MB,导入表里没有 `libiconv-2.dll`,在没有 MSYS2 的 PATH 下正常启动。
2. **栈保留减半。** 链接器默认值不同:GNU ld 的 Windows 默认是 2 MiB,LLD 是 1 MiB。这是主线程和所有未指定栈大小的线程的默认大小(`std::thread`、Boost 线程池都是),
   深递归(JSON 解析、Beast 处理)可能在 GCC 下没事、在 Clang 下溢出。验证:链接时加 `-Wl,--stack,2097152`,PE 头里变回 2 MiB。
3. **运行库本身没有差别。** 两个编译器都用 libstdc++ 16.2 的头文件和库(MSYS2 的 Clang 默认就是 libstdc++,不是 libc++)、UCRT、libgcc 和 libwinpthread,
   都是 `-static` 链接,安装器不需要带任何 C++ 运行库 DLL。第三方库(curl、OpenSSL、Opus、miniupnpc 等)都是 libstdc++ 的预编译版本,
   换 libc++ 需要整个依赖栈重建(MSYS2 的 CLANG64 环境),不值得。

不同时刻的对比只反映抽到的虚拟机。带预编译头的两次 889 s 和 1316 s 同样落在这种波动里,不能作为证据。

| Clang 对 GCC | 0.70–0.88×(三台虚拟机),但落到整个作业里被 Boost、链接、打包、最重的单个文件和工具链安装稀释 |

| lld 对 GNU ld | 无收益(此前实测) |

### Clang 构建本身的质量

- 运行时:同一虚拟机上交替运行,用各自编译器编译的 FEC 编码器,当时 Clang 编码快 12%、解码快 14%(托管 runner 一次测量;固定主机上没有复现,见上文「运行时微基准」)。
  `sunshine.exe` 85.1 MB(GCC 101.0 MB),符号表仍在(14.3 万个,GCC 22.4 万个),崩溃符号化仍可用。
- 警告:把全部 Clang 警告清零(缺 `override`、未使用的成员和常量、布尔上的 `|`、C++ 里的变长数组、多余的 lambda 捕获、
  `dllexport` 重复声明、仅 GCC 认识的 `-Wno-` 选项、Boost 头文件按系统头处理),没有用笼统的 `-Wno`。
- `HttpSafety.SingleHttpsThreadRemainsResponsiveAndDisconnectCancelsAllStreams` 失败的原因是测试辅助函数
  `wait_until` 在条件成立后又求值一次,而条件 `submit_stream` 每成功一次就占一个许可,第二次可能找不到空位。
  与编译器无关(Linux 上两种编译器的复现程序约 50% 失败),GCC 只是时序上躲过。已改为每轮求值一次,并先等全部许可归还。
  修复后所有运行都通过,另外 `ctest --repeat until-fail:10` 也通过。

### 这次运行遇到的失败

Clang 第 2 次运行的 `test_sunshine` 在 `Poster` 测试里以 `0xc0000409` 退出:
`filesystem error: cannot remove all ... source.png ... being used by another process`。
`src/nvhttp/poster.cpp` 起了一个分离的后台线程生成预览,测试在预览出现后马上 `remove_all` 临时目录,
后台线程可能还开着 `source.png`,Windows 上就是共享冲突。这是测试与后台线程之间的竞态,不是编译器的代码生成问题,
但它在 Clang 的完整运行里出现了 2 次(17 次中),在 GCC 的完整运行里 0 次(8 次中),时序相关。
没有修(切换已不再推进);如果以后切换,要先让测试等后台线程结束或对 `remove_all` 做重试。

### 与编译器无关、值得单独合入的部分

1. `HttpSafety` 测试辅助函数的修复(真实竞态)。
2. `CCACHE_DEPEND=1`:GCC 也受益(未命中路径快约 9%),命中不变。
3. Clang 暴露的标准符合性问题(`VdfNode` 的不完整类型、枚举范围外的 `constexpr` 转换)。

## 建议

**有条件采用:发布构建改用 Clang(MSYS2 UCRT64 的 Clang + libstdc++ + LLD + 预编译头),GCC 保留为回退(`CI_TOOLCHAIN` 变量或手动运行的 `toolchain` 输入)。下面的条件满足之前不要切换。**

**为什么采用。** 同一台机器上交错重复:
- 冷构建墙钟 0.66×、CPU 0.57×;
- `sunshine.exe` 小 15.7%;
- 运行时与 GCC 持平;
- 86 个 ctest 条目的失败集合逐项相同(各 10 次);
- 警告为 0。

**数据不支持的。**
- 运行时收益:FEC、数据包拆分持平,FEC 解码慢 5%。
- 热构建收益:持平。
- 托管 runner 上的端到端收益:此前三次对三次没有可靠差别。如果目标是日常 CI 时间,这些数据不支持切换;如果只用于发布构建,冷构建和体积的收益才是主要理由。
- 「快 34%」里约三分之二是预编译头。**只给 GCC 开 `SUNSHINE_PRECOMPILED_HEADERS`,冷构建就从 940 s 到 694 s(−26%)**,构建通过(该配置的测试没有单独跑),不换编译器、没有下面的任何风险,可以先做。

**条件(都已验证可行,必须在切换的同一次改动里完成):**
1. **修两处链接差异。** 去掉显式的 `libiconv.dll.a`(让 `-liconv` 在 `-static` 下取静态库),并给 Clang 的链接加 `-Wl,--stack,2097152`。
   已在重新链接的 `sunshine.exe` 上验证:导入表没有 `libiconv-2.dll`,栈保留 2 MiB,在没有 MSYS2 的 PATH 下正常启动,体积 86.2 MB。
2. **CI 门禁。** 对发布产物检查三件事:导入表只含系统 DLL,`SizeOfStackReserve` 不小于 2 MiB,并在一个没有 MSYS2 的环境里执行 `sunshine.exe --version`。
   现在的测试都在装了 MSYS2 的机器上运行,第一项问题不会被发现。
3. **先修 `Poster` 测试与后台线程的竞态。** 托管 runner 上 Clang 下 17 次里失败 2 次、GCC 下 8 次里 0 次;不修的话 Clang 流水线会随机变红。
4. **在 Windows 虚拟机上用 Clang 产物完整跑一遍发布门禁,并补上本文缺的虚拟机微基准。** 若 FEC 或数据包拆分比 GCC 慢超过 5%,回到 GCC。
5. **日常 CI 是否也用 Clang 另行决定。** ccache 缓存是 5 倍(464 MB 对 91 MB),托管 runner 上每次还原和保存都要多花时间,这可能是此前端到端没有收益的原因之一;
   只在发布构建用 Clang 时这一项可以忽略。

**没有验证的。** Windows 虚拟机上的微基准;原生 Windows 上完整的测试套件(Wine 里 GPU、驱动、NVAPI 相关条目无法运行);Clang 版多出的 14 个 API 集在旧版 Windows 上是否都存在;
修好链接后在托管 runner 上的端到端时间;`audio-info.exe` 在 Clang 下变大 3.2 倍的原因。
